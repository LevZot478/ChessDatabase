# Подготовка к защите лабораторной №2

## 1. Что сказать в начале — примерно одна минута

«Я реализовал файловую базу данных участников шахматного клуба на Java с графическим интерфейсом Swing. В одной таблице шесть полей: уникальный ID, имя, рейтинг, взнос, дата регистрации и признак активности.

Записи хранятся в двоичном файле players.dat. Для ускорения операций по ключу используется отдельный файловый хеш-индекс players-id.idx: он связывает ID с номером слота записи. Данные читаются и изменяются через RandomAccessFile непосредственно в файле. Вся база для обработки в коллекцию не загружается; таблица в памяти используется только для отображения.

Реализованы создание, открытие, удаление, очистка и сохранение базы, добавление с проверкой уникальности, поиск, редактирование и удаление. По неключевым полям обрабатываются все совпадения. Есть резервное копирование, восстановление и дополнительная выгрузка в CSV. Для проверки использованы автоматические тесты, а для сравнения алгоритмов измерено время операций».

Не нужно заучивать дословно: обязательно понимать, как ID превращается в адрес записи.

Разделение нужно, чтобы изменение кнопок не меняло формат хранения, а проверку алгоритмов можно было запускать без GUI.

## 3. Поля и ограничения

- ID: положительное целое int, уникальное ключевое поле.
- Имя: непустая строка до 50 кодовых единиц UTF-16, внешние пробелы убираются.
- Рейтинг: int от 0 до 4000.
- Взнос: конечный неотрицательный double.
- Дата: LocalDate, в файле хранится число дней относительно 1970-01-01.
- Активен: boolean.

В интерфейсе взнос принимает и запятую, и точку. Важные ограничения дополнительно проверяет Player, поэтому их нельзя обойти простым вызовом метода вне GUI. Для реальной финансовой системы вместо double лучше использовать целое число копеек или BigDecimal: double имеет погрешность представления дробей.

## 4. Как устроен файл данных

Заголовок players.dat занимает 16 байт: признак формата, версия и указатель на первый свободный слот. Размер записи Player — 125 байт: ID 4 + имя 100 + рейтинг 4 + взнос 8 + дата 8 + активность 1.

Слот занимает 134 байта: флаг занятости 1 + ссылка на следующий свободный слот 8 + запись 125. Поэтому начало слота с номером s вычисляется так:

`offset = 16 + s * 134`

Например, слот 2 начинается по смещению 284. RandomAccessFile.seek(offset) перемещает позицию чтения/записи к этому месту. Не нужно читать все предыдущие записи.

Удаление помечает слот свободным и добавляет его в связный список свободных слотов. Файл целиком не переписывается. При добавлении сначала используется свободный слот; если их нет, файл увеличивается. Номер слота — физическое место, ID — логический ключ; это разные величины.

## 5. Как работает индекс

В players-id.idx находятся заголовок 12 байт, массив указателей на корзины (8 байт на корзину) и узлы по 20 байт: ID 4 + номер слота 8 + ссылка на следующий узел 8. И корзины, и цепочки находятся в файле.

Корзина вычисляется как `floorMod(id, числоКорзин)`. Изначально корзин 4099. ID 1, 4100 и 8199 попадают в одну корзину — это коллизия. Цепочка хранит несколько узлов, при поиске сравнивается полный ID, а не только номер корзины.

Поиск: вычислить корзину → пройти её цепочку → получить слот → прочитать запись из players.dat.

Если после вставки отношение числа записей к числу корзин превысит 0,75, индекс расширяется: B → 2B + 1. Узлы последовательно переносятся во временный файл с пересчётом корзин; новый индекс заменяет старый. Вся база в память не загружается. Это расширение индекса, а не запрещённая обработка массива записей с полной перезаписью базы.

## 6. Что происходит при основных операциях

**Добавление:** проверить поля → проверить отсутствие ID в индексе → записать данные в свободный/новый слот → добавить ID и слот в индекс.

**Изменение:** найти старую запись → проверить новый ID → записать новые данные в тот же слот. Если ID изменился, удалить старый ключ из индекса и добавить новый.

**Удаление по ID:** найти слот через индекс → освободить слот → исключить узел из цепочки индекса.

**Поиск по неключевому полю:** последовательно читать слоты и показывать каждую живую запись с точным совпадением. Индекса на имя/рейтинг нет. Удаление по неключевому полю тоже обрабатывает все совпадения.

**Сохранение:** изменения выполняются непосредственно в файлах, а save вызывает синхронизацию файловых дескрипторов с устройством хранения. Это не сериализация таблицы GUI.

**Резервная копия:** после сохранения два служебных файла упаковываются в ZIP. При восстановлении создаётся отдельная папка, проверяются файлы и согласованность данных с индексом.

## 7. Сложность — это обязательно знать

Обозначения: n — число живых записей; S — число выделенных слотов, включая удалённые; B — число корзин. После массового удаления S может быть намного больше n.

| Операция | Оценка и условия |
|---|---|
| Чтение известного слота | O(1) при фиксированной длине записи |
| Поиск/удаление по ID | Ожидаемо O(1) при хорошем распределении; худший случай O(n) |
| Добавление | Ожидаемо амортизированно O(1); отдельное расширение O(n + B) |
| Изменение без смены ID | Ожидаемо O(1), худший случай O(n) |
| Изменение со сменой ID | Как поиск + удаление + вставка; возможно расширение |
| Поиск по неключевому полю | O(S) |
| Удаление по неключевому полю | Ожидаемо O(S); при плохих коллизиях вплоть до O(S + n²) |
| Показ всей базы / CSV | O(S), дополнительная память экспортера O(1) при фиксированных полях |
| Открытие индекса | O(B + n): обход цепочек для подсчёта записей |
| Backup | Линейно по суммарному размеру файлов |

«Ожидаемо» относится к распределению ключей и длине цепочек. «Амортизированно» означает среднюю стоимость на длинной последовательности операций, с учётом редких дорогих расширений. Это не гарантия, что каждая вставка занимает одинаковое время.

Обновление таблицы GUI после изменения требует отдельного полного прохода. Поэтому быстрое изменение в файловом ядре не означает O(1) для всей кнопки вместе с перерисовкой. Выгрузка и другие долгие операции пока выполняются в потоке GUI и на большой базе могут временно блокировать окно.

## 8. Замеры и их правильная интерпретация

Среднее время одной операции, микросекунды, по полученному запуску PerformanceCheck:

| Записей | Добавление | Поиск через индекс | Поиск перебором | Удаление |
|---:|---:|---:|---:|---:|
| 100 | 424,66 | 271,26 | 8942,31 | 510,46 |
| 1000 | 356,97 | 181,24 | 82133,29 | 253,04 |
| 5000 | 342,06 | 176,82 | 426504,27 | 239,56 |

Вывод: перебор существенно дорожает с ростом базы; индексированный поиск в этих замерах гораздо быстрее. При 5000 записях отношение примерно 2412 раз. Времена не являются доказательством асимптотики: влияют прогрев JVM, кэш ОС и диск. Подготовка данных и save находятся вне измеряемых участков; эти числа не показывают стоимость принудительной синхронизации после каждой записи. Замер вставки в подготовленную базу сам по себе не доказывает амортизированную оценку расширения.

## 9. CSV: как показать и объяснить

Нажать «Выгрузить CSV», выбрать новое имя файла и открыть результат в Excel/LibreOffice. Выгружаются все живые записи текущей базы, независимо от фильтра и сортировки таблицы. Исходная база не меняется, существующий файл не перезаписывается.

Формат: UTF-8 с BOM, разделитель `;`, десятичная запятая, дата YYYY-MM-DD, активность true/false. Имя заключено в кавычки; внутренние кавычки удваиваются. Это сохраняет имена с разделителями и переносами строк. Для имени, начинающегося с =, +, - или @, добавляется апостроф, чтобы табличный редактор не трактовал текст как формулу; это намеренное изменение представления в выгрузке.

Если редактор показывает одну колонку, открыть через импорт текстового/CSV-файла и выбрать UTF-8, разделитель «точка с запятой», десятичную запятую. CSV — дополнительный внешний формат, а не XLSX. Он не сохраняет оформление, индекс и свободные слоты. Обратный импорт CSV не реализован; для восстановления используется ZIP-backup.

В задании написано «импорт БД в файл стороннего формата», но направление «из БД в файл» технически является экспортом. Реализована именно выгрузка в дополнительный формат.

## 10. Сценарий демонстрации на 5–7 минут

Использовать отдельную демонстрационную базу, чтобы не менять свои рабочие данные.

1. Создать базу. Добавить три записи, у двух одинаковый рейтинг.
2. Попытаться добавить существующий ID: показать отказ без появления дубликата.
3. Найти запись по ID; найти по общему рейтингу и показать оба совпадения.
4. Изменить имя/взнос; показать результат. При смене ID показать поиск по новому ключу.
5. Создать ZIP-копию. Удалить по общему рейтингу — должны исчезнуть все совпадения.
6. Восстановить копию в новую папку: записи вернулись. Выполнить «Проверить БД».
7. Выгрузить CSV, открыть таблицу, показать шесть колонок и кириллицу.
8. Сохранить и переоткрыть базу. На отдельной ненужной базе показать очистку и удаление; текущую открытую базу программа удалить не разрешает.
9. Показать результаты PerformanceCheck и объяснить разницу индекса и перебора. При вопросе о надёжности показать ConsistencyCheck, IndexGrowthCheck и CsvExportCheck.

## 11. Вопросы преподавателя и короткие ответы

**Почему это БД, а не просто таблица в окне?** Данные сохраняются в собственном файловом формате, есть ключ, проверки, операции поиска/изменения, индекс и восстановление. GUI только управляет ими.

**Почему не HashMap?** В этом задании обработка базы через загруженную коллекцию запрещена. Хеш-таблица реализована на диске.

**Разве DefaultTableModel не нарушает запрет?** По условию разрешена загрузка для визуализации. Действия выполняются через PlayerDatabase и исходные файлы, не через сохранение модели таблицы.

**Зачем фиксированная длина?** Адрес слота вычисляется арифметически, а изменение записи не сдвигает следующие записи. Цена — ограничение длины имени и резервирование места.

**Почему нельзя считать ID номером слота?** ID может быть большим и разреженным, а слоты переиспользуются после удаления. Индекс связывает эти разные понятия.

**Что происходит при коллизии?** Идём по цепочке узлов одной корзины и сравниваем точный ID.

**Почему индекс увеличивается?** Чтобы ограничивать среднюю длину цепочек при росте числа записей. Ключи нужно перераспределить, потому что меняется делитель хеш-функции.

**Поиск всегда O(1)?** Нет. Ожидаемо при хорошем распределении. В одной длинной цепочке — O(n).

**Почему поиск по имени медленный?** На имя нет индекса, поэтому нужен полный просмотр слотов. Дополнительный индекс ускорил бы поиск, но усложнил изменения и занял место.

**Сжимается ли файл после удаления?** Обычное удаление не сдвигает данные; освободившиеся слоты используются повторно. Старые узлы индекса могут оставаться недоступными до перестроения.

**Backup и CSV — одно и то же?** Нет. ZIP сохраняет внутренние файлы для восстановления, CSV предназначен для просмотра/обмена записями.

**Есть ли транзакции и защита от внезапного выключения?** Полноценных транзакций нет. Данные и индекс меняются последовательно, поэтому сбой между записями может нарушить согласованность. save не делает две записи атомарными. Есть проверка и резервные копии; для следующего этапа нужен журнал восстановления.

**Можно открыть базу двумя процессами?** Безопасная многопользовательская работа и блокировки не реализованы; предусмотрена работа одного экземпляра.

**Что доказывают тесты?** Проверяют конкретные сценарии: корректные операции, дубликаты, коллизии, рост и повторное открытие индекса, обнаружение повреждений, CSV. Они не доказывают отсутствие всех возможных ошибок.
